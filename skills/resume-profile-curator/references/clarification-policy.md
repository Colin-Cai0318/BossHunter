# 补充问题策略

每轮最多 5 个问题，只问会改变档案结论的缺口。

优先级：

1. 个人贡献未知。
2. 同一实体字段冲突。
3. 有数字结果但缺口径或来源。
4. Action 明确但 Result 缺失。
5. 派生技能尚未确认。

问题必须指出对应经历和缺口，请用户提供真实、可面试解释的信息；不得给出可直接照抄的虚构示例。回答保存为独立确认记录，不修改原文证据。

## 中文提问与冲突说明

- 默认面向中文母语用户，所有用户可见的问题、字段名和回答指导使用自然简体中文；不得暴露 company、position、group_id 等内部字段名。
- 问题先说明“系统目前知道什么、缺少什么”，再提出一个可直接回答的决策点。避免只写“请补充信息”“有多个值”等抽象提示。
- 两条信息内容完全相同时视为重复事实，不生成冲突问题。
- 两条信息内容不同时称为“不一致”，不得笼统称为“重复”。必须用“选项 1/2”逐项列出字段值、材料名称、所属经历线索和原文证据。
- 冲突问题必须允许用户直接回答“保留选项 1/2”，或说明各选项分别属于哪家公司、项目或时间段。

## 草稿 review 后的追问

- 先让用户看到证据安全草稿，再根据未使用事实、Known Gaps 和被剔除表达生成问题；不要在首轮要求用户填写长表单。
- 同一项目的问题合并处理，优先询问个人负责范围、实际使用场景、结果口径和可以公开的量化数据。
- 每个问题说明回答后会改变哪条 STAR、贡献动词或项目排序。
- 用户选择目标岗位后，允许调整事实选择、篇幅和顺序，但不得把岗位名称或关键词当作新事实加入；生成结果的质量报告应记录本次目标岗位，便于 review。

## 问题卡片契约

每个问题必须同时提供：

- 明确的问题类型，不用数字优先级代替含义。
- 当前已有事实或动作摘要，让用户知道系统在追问哪一条内容。
- 具体问题，只问一个决策点。
- 回答格式指导，使用占位结构而非可照抄的虚构答案。
- 回答后将改变的正文位置、STAR 字段或贡献动词。

用户确认的实质回答是新增证据，生成时必须优先融合到对应正文。Known Gaps 与表达边界只在审核面板和 JSON 中保留，不得出现在预览、下载或启用的 Markdown 正文。
